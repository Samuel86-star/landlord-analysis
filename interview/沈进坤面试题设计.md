## 第一部分：系统架构与分布式（权重 25%）

### 题 1：注册中心选型 — Eureka → Nacos 迁移

你在数字权益平台项目中做过 Eureka 到 Nacos 的迁移，用了 NacosSync 做过渡。请展开讲：

**主问题**：Eureka AP 模型和 Nacos 同时支持 AP/CP 模型，在实际迁移过程中，你们是如何处理服务发现的语义差异的？迁移期间，有没有遇到过"注册中心数据不一致导致流量打到已下线节点"的问题，怎么解决的？

**追问方向**：
- NacosSync 在双向同步时，如果两边同时有注册/注销操作，冲突如何仲裁？
- Eureka 自保护模式下，所有实例都"可用"——你当时怎么判断真实的下线节点？
- 如果让你重来一次，你会选 Nacos 的 AP 还是 CP 模式，为什么？

**评分标准**：
- 只答"NacosSync 自动同步" → 浅层，未触及核心问题
- 能说出 CAP 在注册中心的具体体现和双写冲突 → 中
- 能结合生产故障案例说明自保护机制的坑和双向同步的一致性边界 → 深

**优秀回答参考**：

> 这道题的深度在于"CAP 不是选择题，而是你理解不一致窗口的时长和后果"。期望候选人能触及以下层次：

**第一层：语义差异的本质。** Eureka 是纯 AP 模型，每个节点都可以接受注册和查询，没有 Leader 概念；实例状态通过心跳续约，默认 90s 无心跳才剔除。Nacos 可以选择 AP 或 CP——CP 模式下走 Raft 协议，注册/注销是线性一致的操作。迁移期间，关键差异在于：Eureka 侧一个实例下线后，在心跳超时窗口内其他调用方仍然能查到该实例；Nacos CP 侧下线的传播是 Raft 提交即生效，理论上更快。两者的不一致窗口不同，NacosSync 只能做到最终一致，所以迁移期间调用方必须保留 client 端的重试/熔断机制。

**第二层：双写冲突的实际处理。** NacosSync 双向同步时，冲突仲裁实际上取决于"谁先被同步到对端"。因为没有全局时钟或 Version Vector，同时发生的注册/注销大概率一方覆盖另一方。期望候选人能说出他们实际的做法：比如迁移期间只做单向同步（Eureka→Nacos），业务方先在 Nacos 侧注册，验证稳定后再停掉 Eureka 侧——而不是自信地做双向同步。battle-tested 的架构师知道"双向同步是一个伪需求，生产中最安全的是单向 + 灰度切流"。

**第三层：自保护模式的坑。** Eureka 自保护模式的触发条件是 15 分钟内心跳续约比例低于 85%，一旦触发就不会剔除任何实例。期望候选人能说出他们在监控上做了什么——比如对比 Eureka 的实例列表和实际 K8s Pod 的存活状态，或者在 client 端加了 health check 的二次验证。真正的教训是：注册中心的"可用"是注册中心的视角，不是业务视角；client 端必须在负载均衡层面有自己的熔断逻辑（比如 Ribbon 重试 + Hystrix 熔断）。

**第三层延伸：选 AP 还是 CP 的工程判断。** 重来一次大多数有经验的架构师会选 AP。原因：注册中心的核心功能是"服务发现"，短时间的不一致（几百毫秒到几秒）远比注册中心自身不可用危害小。CP 模式在发生网络分区时，如果当前节点不在 Raft 多数派里，它会拒绝所有写操作——这意味着新服务可能注册不上。但对于金融/支付等强一致性场景，CP 也有其价值。关键不在于选哪个，而在于"你清楚你选的代价是什么"。

### 题 2：分布式一致性实践

你在 108 社区和智慧城市 SaaS 平台中都用了 RabbitMQ/RocketMQ 做异步通讯。

**主问题**：假设有一个"用户下单后扣减库存并发放积分"的场景，订单服务、库存服务、积分服务都在独立的数据库中。你们如何保证这三个操作的数据最终一致性？具体用过什么模式，踩过什么坑？

**追问方向**：
- RocketMQ 的事务消息和 RabbitMQ 的 publisher confirm + 本地消息表，你分别会在什么场景选哪个？
- 如果消费方处理成功了，但发送方本地事务回滚了怎么办？
- 你们的对账机制是怎么做的？T+1 离线对账还是准实时补偿？

**评分标准**：
- 只答"用 MQ 异步" → 浅
- 能对比不同方案的事务保证力度和适用场景 → 中
- 能从"消息发送+本地事务非原子"出发，讲清半消息/事务回查/补偿的完整链路 → 深

**优秀回答参考**：

> 这道题是检验候选人是否真正在分布式系统中"流过血"的核心题。期望的回答应该展现出一条逐步进化的轨迹，而非一次给出完美答案。

**第一层：方案选型与演进路径。**

新手方案是"先写订单库，再发 MQ"——这有明显的原子性问题：订单入库后进程崩溃，MQ 没发出去。进阶方案是本地消息表（Outbox Pattern）：在订单库的同一个事务里写入订单 + 一条 outbox 记录，然后用一个独立的后台线程轮询 outbox 表发送 MQ。这一步解决了"本地事务和消息发送的非原子问题"。但如果技术栈选了 RocketMQ，可以直接用事务消息（半消息机制）替换掉轮询 outbox 的部分。

期望候选人能说出两层判断逻辑：如果是自建机房、团队有能力维护好 outbox 轮询机制，RabbitMQ + outbox 是最稳妥的；如果用的是阿里云且 RocketMQ 版本支持事务消息，可以直接用事务消息省掉 outbox 表。但要注意 RocketMQ 事务消息的回查接口如果实现不当（比如回查逻辑里又查了一次业务库但查不到——因为业务事务确实还没提交），会导致消息大量回滚。

**第二层：消费端的幂等与补偿。**

消费方处理成功但发送方本地事务回滚——这是"事务消息"才有的语义。RocketMQ 的处理方式是：如果发送方事务回滚，半消息不会被投递，消费方根本收不到。但 outbox 模式不同：如果 outbox 里写入了消息但业务事务最终回滚了，这就是"脏消息"。期望候选人能说出实际的补救——outbox 表里加一个 status 字段（PENDING/CONFIRMED/CANCELLED），后台轮询时检查关联的订单状态，如果订单已被取消则不发送。这恰恰说明：outbox 模式的正确性依赖于你正确地设计了确认机制。

**第三层：对账——分布式系统的最后一道防线。**

不管前面设计得多好，都该有对账。期望的答案是：T+1 离线对账 + 实时异常告警相结合。离线对账每天凌晨跑一个批处理，比对订单表、库存扣减流水表、积分发放表的差异，生成差异报告。实时层面：关键业务指标（比如订单创建数 vs 库存扣减数 vs 积分发放数）通过监控面板实时对比，差异超过阈值就告警。最有经验的候选人还会提到：他们让对账脚本的产物不是一张差异表，而是一条自动补偿流水——对于明确是系统遗漏的（比如订单已支付但积分未发放），自动触发补偿。这才是真正的"最终一致性"闭环。

## 第二部分：JVM 与性能调优（权重 20%）

### 题 3：GC 策略实战

**主问题**：假设你们 108 社区的线上服务出现了偶发性 Full GC，每次约 2-3 秒，导致部分请求超时。请完整描述你的排查和解决思路——从发现问题到最终修复的全过程。

**追问方向**：
- 你怎么确定是 GC 导致的 RT 抖动，而不是其他原因（如数据库慢查询、网络抖动）？
- 有没有遇到过"调了 GC 参数后吞吐量反而下降"的情况？为什么？
- 你实际项目中最常使用的 GC 组合是什么？如果给你一个 8G 堆、对延迟敏感的服务，你会怎么配参数？

**评分标准**：
- 只答"调大堆内存"或"换 G1" → 浅
- 能从 GC 日志中提取分析线索，给出调优决策依据 → 中
- 能综合评估"调参数 vs 改代码内存泄漏 vs 增加机器"的收益 → 深

**优秀回答参考**：

> 这道题考的不是"你知道 G1 和 CMS 区别"，而是"你会怎么从一个模糊的现象定位到根因"的排查思维。

**第一层：定界——确认是 GC。** 第一步不是看 GC 日志，而是对比时间线。从监控（Prometheus/Grafana）拉出三张图：接口 RT 分布、JVM GC 次数和耗时、系统 CPU 使用率。如果 RT 抖动和 GC 耗时的尖峰在时间上完全吻合，基本可以确认。同时排除其他干扰：数据库慢查询有独立的 SQL 监控，网络抖动看 TCP 重传率和连接超时日志。如果 JVM 进程的 CPU 在 RT 抖动期间反而高涨——这是 Full GC 的典型特征（Stop-The-World 期间所有业务线程暂停，GC 线程吃满 CPU 做标记和压缩）。

**第二层：分析 GC 日志。** 打开 `-Xloggc` 日志，重点关注几点：Full GC 前后的老年代占用率（Full GC 前老年代是否接近 100%，Full GC 后能回收到多少——如果回收量很少说明是真内存不够，如果回收到很低说明有大对象临时填充）。同时看年轻代晋升到老年代的平均大小——如果平均晋升特别大，说明对象过早晋升（Premature Promotion），年轻代太小。还要数 CMS 的 concurrent mode failure 次数——这是 CMS 的经典坑：并发清理过程中老年代又满了，被迫降级为 Serial Old 做单线程 Full GC。

**第三层：根因判断与修复优先级。** 只有两种根因：内存泄漏，或内存确实不够用。区分方法：看 Full GC 后的老年代占用是否随时间单调递增。如果是泄漏——堆 Dump（`jmap -dump`），MAT 分析，查 Dominator Tree 找到占用最高的对象。如果是配置问题——根据对象生命周期调整年轻代/老年代比例。期望候选人能举例：比如一次排查发现是 ThreadLocal 没有 remove 导致泄漏，或者是一个本地缓存没有设置大小上限。

**第四层：GC 选型的实战思考。** 对于 8G 堆 + 延迟敏感，首选 G1。核心参数：`-XX:MaxGCPauseMillis=200`（设 200ms 作为暂停目标）、`-XX:G1HeapRegionSize=4m`（Region 大小 = 堆大小 / 2048 左右，8G 下大概 4M）、`-XX:InitiatingHeapOccupancyPercent=45`（老年代占用达到堆的 45% 时触发 Mixed GC，比默认 45% 保守一些）。同时预留 `-XX:+ParallelRefProcEnabled` 加速引用处理。如果堆小于 4G，CMS 仍可考虑；大于 16G 且延迟要求不极端，G1 也是首选。真正极端的低延迟场景（<10ms 暂停）才考虑 ZGC/Shenandoah。

候选人如果能说出"调了 GC 参数吞吐下降是因为 GC 变频繁但单次暂停变短了——CPU 花在 GC 上的总时间变多了"，说明真正理解 GC 调优的本质是"暂停时间 vs 吞吐"的 trade-off。

### 题 4：HotSpot JIT 编译的坑

**主问题**：你了解 JIT 编译中的"逃逸分析"和"栈上分配"吗？你有没有在生产环境遇到过"同一段代码预热前后性能差一个数量级"的情况？你们怎么做的预热？

**追问方向**：
- `-XX:+PrintCompilation` 输出的日志你会怎么解读？
- C1 和 C2 编译器分别在什么时候介入？什么场景下 C2 编译反而更慢（如大量 deoptimization）？
- 你的微服务在发布后是否需要预热？如果有，你们的预热策略是什么？

**评分标准**：
- 不知道或不了解 → 扣分（17年经验应有所接触）
- 能讲清概念但没实战经验 → 中
- 能结合线上 JIT 编译日志或 deoptimization 案例说明 → 深

**优秀回答参考**：

> 这道题定位为"区分科班老兵和纯业务 CRUD 老兵"的关键题。JIT 的实战理解是一道分水岭。

**第一层：概念框架。** 逃逸分析（Escape Analysis）是 JIT 判断对象作用域的关键优化——如果一个对象不会逃逸出当前方法或当前线程，就可以做栈上分配（Stack Allocation）和标量替换（Scalar Replacement），避免在堆上分配内存，从而减轻 GC 压力。JDK 6u23 之后默认开启。一个经典的例子是方法内的局部 `StringBuilder`——如果它是纯局部的，JIT 可能连对象都不创建，直接拆成多个局部变量。候选人应该能说出：你没办法直接观测栈上分配是否生效，只能通过 GC 频率间接推断——如果一个热点方法里频繁 new 对象但 GC 压力很小，大概率逃逸分析在起作用。

**第二层：PrintCompilation 日志的实战解读。** 每行日志的格式是：`时间戳 编译ID 属性% 编译级别 方法名 @ 字节码大小`。编译级别 3 是 C1 编译，4 是 C2 编译。如果看到同一个方法反复出现编译日志，说明被 deoptimization（去优化）后又重新编译了。Web 服务最常见的是"类层次去优化"（CHA 去优化）：编译时假设某个接口只有一个实现类，做了内联；运行时加载了第二个实现类，触发去优化。候选人如果能说出 `-XX:+PrintInlining` 和 `-XX:+LogCompilation` 配合 JITWatch 的分析流程，就是实战派。

**第三层：预热的工程实践。** 微服务发布后的预热不是"启动后先睡 30 秒"，而是主动构造流量让 JIT 触发编译。做法包括：启动后用 JMeter/ab 发送一波预热请求，或者用 K8s 的 readiness probe 在 pod 就绪后才接入流量（但 pod ready 不等于 JIT 预热完成）。更有经验的做法：设置 `-XX:CompileThreshold=1000`（降低触发 JIT 的门槛，加速预热），同时在 CI 里跑 AOT（AppCDS / GraalVM Native Image）把热点代码预编译进共享归档文件。候选人还应该知道预热的不只是 JIT——还有连接池初始化、框架的懒加载、OS 的 page cache 预热等。

如果候选人能举出现实例：比如"上线后前 5 分钟 RT 是稳定后的 3 倍，排查发现是因为 C2 编译还没触发，简单调整 readiness probe 的 initialDelaySeconds 没用，最后还是加了启动预热脚本"，这就是非常好的回答。

## 第三部分：数据库与存储（权重 20%）

### 题 5：千万级用户系统的 SQL 优化

你的用户系统支撑 400+ 游戏接入，服务了大量用户。

**主问题**：假设你们的用户表（MySQL）已经达到 5000 万行，索引加了但慢查询仍然很多。请从索引设计、SQL 改写、架构层面三个维度，说说你的优化思路。特别注意：你之前用的是 SQL Server + DDD 架构，和 MySQL 在优化器行为上有哪些差异？

**追问方向**：
- SQL Server 和 MySQL 在查询优化器上的关键差异是什么？（如统计信息更新策略、索引选择逻辑）
- `SELECT * FROM user WHERE id IN (...)` 一千个 ID，MySQL 优化器会怎么执行？会不会走索引？会不会出现 index dive 问题？
- 如果必须分库分表，你会选什么中间件？sharding key 怎么选？

**评分标准**：
- 只答"加索引" → 浅
- 能分析慢查询日志、合理评估索引选择性、区分覆盖索引和回表 → 中
- 能从优化器行为差异、分库分表方案取舍、以及"分库分表带来的分布式事务/跨 shard 查询"问题出发 → 深

**优秀回答参考**：

> 这道题的核心考察点是"性能优化不是加索引，而是理解优化器为什么会选错索引，以及什么时候必须动架构"。

**第一层：索引设计的实战原则。** 5000 万行表上的索引问题往往是"索引多但选择性差"或"索引选择性好但优化器不选"。第一条原则：用 `EXPLAIN` 看执行计划里的 `key_len`——确认优化器实际用了哪个索引，索引的前缀字段是否发挥了作用。如果发现 `possible_keys` 有多个但 `key` 为 NULL，说明优化器评估下来全表扫描的 cost 低于走任何索引——这通常是因为索引的选择性太差（比如 status 字段只有 3 个值，走索引反而会触发大量回表）。第二条原则：覆盖索引优先——如果查询只涉及 3-4 个字段，建一个包含所有查询列的联合索引，让优化器走 `Using index`（覆盖索引），省掉回表。第三条原则：联合索引的列顺序必须和查询的 WHERE/ORDER BY/GROUP BY 对齐——尤其是范围查询（`>` `<` `BETWEEN`）后面的索引列会失效。

**第二层：SQL Server vs MySQL 优化器差异。** 这是一个很好的区分点——沈进坤横跨两个生态，应该有体会。关键差异有三：(1) SQL Server 的统计信息是自动异步更新的，有采样率；MySQL InnoDB 默认也是自动更新的（`innodb_stats_auto_recalc`），但采样页数是固定的 20 页（`innodb_stats_persistent_sample_pages`），大表下样本不够会导致统计信息不准。所以 MySQL 大表下经常需要手动 `ANALYZE TABLE`。 (2) SQL Server 的查询优化器是"基于成本"（Cost-Based）且有一个超时机制——优化阶段超时了就选当前最优，不会穷举；MySQL 的优化器相对轻量，对复杂查询（多表 JOIN）的 plan 选择更容易出错，这时得靠 `STRAIGHT_JOIN` 强制驱动表顺序。 (3) SQL Server 有 Index Seek 和 Index Scan 的清晰区分；MySQL 的 EXPLAIN 里 `type` 字段（`ref`/`range`/`index`/`ALL`）需要结合 `Extra` 才能完整理解。候选人如果不知道这些差异，说明他对"自己的查询在不同数据库上可能截然不同"缺乏警惕。

**第三层：IN 大列表和 index dive。** `WHERE id IN (1, 2, 3, ..., 1000)`，MySQL 优化器需要计算 `IN` 列表里每个值在索引中的分布，这个过程叫 index dive。如果 `IN` 列表太长（> `eq_range_index_dive_limit`，默认 200），优化器会放弃精确 index dive 转而使用索引统计信息估算，估算结果可能严重偏离实际。这会导致优化器"觉得全表扫描更快"——但实际上走主键索引显著更快。解法：(1) 调大 `eq_range_index_dive_limit`；(2) 改写为临时表 JOIN（把 IN 列表插入临时表再 JOIN）；(3) 如果列表是动态的业务数据，考虑业务上是否能缩小范围。

**第四层：分库分表的工程决策。** 5000 万行还没到非拆不可的地步——加从库读写分离、垂直拆分（按业务模块拆库）、或归档历史数据，通常能再撑一年。但如果业务增速确实需要分库分表：(1) 中间件优先 ShardingSphere-Proxy（透明接入、无需改代码），比 MyCat 成熟且社区活跃；(2) sharding key 选 user_id（因为 400+ 游戏接入的核心查询场景都是查某个用户的信息），避免跨 shard 查询；(3) 分片算法用一致性哈希（扩容时减少数据迁移量）；(4) 必须提前规划好——分库分表后跨 shard 的分布式事务怎么办（Seata AT 模式或干脆业务上降级为最终一致），全局唯一 ID 用雪花算法还是号段模式。

### 题 6：Redis 的深度使用

你在多个项目中用 Redis 做缓存层。

**主问题**：你说用 Redis 做"用户系统"的数据缓存。请描述你们的缓存更新策略（Cache-Aside? Write-Through? Write-Behind?），以及在高并发下如何避免缓存雪崩、缓存穿透、缓存击穿？有没有遇到过 Redis 大 Key 或热 Key 导致集群倾斜的问题？

**追问方向**：
- 你用 Redis 集群还是哨兵？选型依据是什么？
- 如果缓存和数据库双写不一致，你们怎么处理？删缓存还是更新缓存？先删还是后删？
- 你接触的 Redis 最大数据量是多少？单实例内存多大？过期键的淘汰策略你怎么配？

**评分标准**：
- 只答"把热点数据放 Redis" → 浅
- 能讲清缓存模式、穿透/击穿/雪崩的应对策略 → 中
- 能结合实际集群架构、大 Key 拆分经验、数据一致性权衡做出深度分析 → 深

**优秀回答参考**：

> 这道题的陷阱在于——候选人可能把"缓存三剑客"（穿透/击穿/雪崩）背得很熟，但一追问实际数据量和集群架构就露馅。

**第一层：缓存模式选型。** 绝大多数 Web 系统用 Cache-Aside（旁路缓存）就够了：读的时候先查缓存，缓存 miss 则查 DB 并回填缓存；写的时候更新 DB 然后删除缓存。Cache-Aside 的优势是简单且容错好——缓存挂了不影响核心读写路径（只是慢一点），Write-Through/Write-Behind 增加了 Redis 写入链路的强依赖。期望候选人能解释这种"简单即安全"的选择，而非为了展示知识而选复杂模式。

**第二层：缓存一致性——先删还是后删？** 这是经典的坑。如果先删缓存再更新 DB：并发读请求在 DB 更新完成前读到旧数据并回填缓存，导致缓存永远是旧的。如果先更新 DB 再删缓存：并发读请求在缓存删除前读到旧缓存数据，但只是短暂不一致（等缓存被删后就正确了）。所以 "先更新 DB 再删缓存" 是主流方案。但删缓存失败怎么办？加一个重试队列（MQ 补偿）。还有一个高级坑：如果缓存删除的时机和另一个写请求的时机交叉，可能产生"写覆盖"—这需要版本号或分布式锁。真正到达这个层次的候选人会承认：追求缓存和 DB 的强一致性是徒劳的，不如接受最终一致 + 合理的 TTL 兜底。

**第三层：大 Key / 热 Key 的真实经验。** 期望候选人能举出具象的例子。比如：一个用户关注列表的 Hash 结构，当用户有几十万粉丝时变成了大 Key——删除时会阻塞 Redis 的单线程。解法：(1) 拆分——把大 Hash 按 hash tag 拆成多个小 key，读的时候并发查然后合并；(2) `UNLINK` 代替 `DEL`，异步删除；(3) 用 `SCAN` 代替 `HGETALL` 分批查。热 Key 则不同——比如一个热点用户的资料被 QPS 打爆，导致单个 Redis 节点 CPU 到 100%。解法：(1) 在客户端做本地缓存（Caffeine + 短 TTL），拦掉 90% 的读请求；(2) 把热点 key 复制多份到不同节点；(3) Redis 6.0+ 的服务端 I/O 多线程能缓解流量压力但不能解决单 key 瓶颈。

**第四层：集群架构选型。** 哨兵模式（Sentinel）解决的是高可用，集群模式（Cluster）解决的是水平扩展。如果单实例内存 8G 以下、数据量可控，哨兵就够——简单且运维成本低。一旦数据量超过单机内存或者 QPS 单机扛不住，必须上集群。集群的代价是：跨 slot 的多 key 操作（如 MGET）和事务受限，且 reshard 和 failover 的复杂度成倍增长。期望候选人能说出"架构选型不是看哪个更高级，而是看你的实际瓶颈在哪"。

淘汰策略：`allkeys-lru`（在全部 key 中按 LRU 淘汰）是最常用的——但在缓存场景下，千万不要用 `noeviction`（内存满了直接报错），那是灾难。`volatile-lru`（只淘汰有 TTL 的 key）是安全的但可能淘汰不够快。如果有些缓存不允许被淘汰（如限流计数器），设置 `noeviction` 配 `maxmemory-policy` per key——不过一般简单系统不用这么复杂。

## 第四部分：微服务架构实战（权重 20%）

### 题 7：微服务拆分与分布式事务

你在代理商系统中把一个业务拆成了 5 个微服务（账户、广告位、排期、结算、效果），在同城游中台也做了类似的拆分。

**主问题**：你提到代理商系统按照业务功能拆了 5 个服务——请复盘一下，这个拆分粒度在实际运行中有什么问题和教训？比如有没有出现"本想解耦，结果变成了分布式单体"的情况？如果让你重做，你会调整吗？

**追问方向**：
- 拆得太细导致一个业务操作需要跨 5 个服务协调，你怎么处理这种分布式事务？
- 服务拆分后，你的 API 网关（Zuul/Gateway）有什么性能瓶颈？有没有做过聚合层的优化？
- 你们怎么定义"服务拆分的边界"？你用什么方法论的——DDD 限界上下文？业务能力？还是团队拓扑？

**评分标准**：
- 只答"拆了之后耦合低" → 浅（理想化，缺真实教训）
- 能坦诚说出拆分过细带来的事务/性能问题 → 中
- 能从实际踩坑出发，结合方法论（DDD/康威定律）给出边界定义的经验原则 → 深

**优秀回答参考**：

> 这道题的分水岭在于：候选人是否坦诚。一个真正踩过坑的架构师会说"拆了之后问题不少"，而不是画完美的架构图。

**第一层：拆分过细的代价。** 代理商系统拆成 5 个服务——账户、广告位、排期、结算、效果——从业务领域看是合理的，但实际操作中：一个"广告主查看自己广告的投放效果并调整排期"的操作，需要跨 4 个服务（效果→排期→广告位→账户鉴权）。如果每个服务调用都是同步 RPC，RT 是 4 次 RPC 累加；如果有一个服务慢，整个链路超时。期望候选人能说出实际解决——比如把"效果数据查询"改成异步推送（效果服务定时把聚合数据推到广告位服务）、或者引入 BFF 层做数据聚合减少前端调用的次数。

**第二层：分布式事务的真实困境。** "广告排期跨多个广告位"——这其实是一个事务：排期服务创建排期，同时需要广告位服务检查资源是否可用。如果广告位检查失败，排期必须回滚。拆成两个服务后，这个本地事务变成了分布式事务。实际做法通常不是上 Seata（太重），而是：(1) Saga 模式——排期服务先 create 一个 draft 状态的排期，然后异步通知广告位服务锁定资源，广告位成功后再回调排期服务把状态改为 confirmed。如果广告位失败，排期服务把 draft 改为 cancelled。(2) 或者在业务上设计成"先锁定再确认"的两阶段提交模式（非 XA，而是业务语义上的两阶段）。关键洞察：不是所有事务都需要强一致性，大部分可以通过业务流程的重试+补偿解决。

**第三层：网关的瓶颈。** Zuul 1.x 是同步阻塞的（每个请求一个线程），在线程池耗尽时直接拒绝请求。Spring Cloud Gateway 是异步非阻塞的（基于 WebFlux），吞吐量通常高一个数量级。但网关的真正瓶颈往往不在网关本身——而在于网关后面的微服务调用链太长。解法：聚合层（或者 BFF）在网关后面加一层，把多个微服务的调用聚合成一个响应返回给客户端。如果候选人提到 GraphQL 在这方面的优势，说明他在关注 API 层的演进。

**第四层：拆分边界的方法论。** 期望候选人不止提 DDD 限界上下文，还能说出实际判断标准：(1) 数据主权——每个服务拥有自己的数据库，不能共享数据库（共享数据库是"分布式单体"的温床）；(2) 变更频率——经常一起改的表放在一个服务里；两个表如果总是同时被修改，拆开只会增加协调成本；(3) 团队匹配——一个服务由一个团队负责（康威定律），如果一个服务太大导致团队内部沟通成本爆炸，才拆。如果候选人承认"代理商系统拆 5 个现在看有点多，结算和效果其实可以合并，因为它们的业务耦合太紧"，这就是诚实的最高分回答。

### 题 8：CI/CD 与 DevOps 实施

你在多个项目中都提到了 GitLab CI/CD 和自动化运维。

**主问题**：你们的 CI/CD 流水线具体怎么设计的？从代码提交到生产上线，有哪些卡点（代码审查、自动化测试、灰度发布、回滚策略）？你们的测试覆盖率要求是多少？

**追问方向**：
- 你们的灰度发布是怎么实现的？网关层配置路由权重还是用 K8s Service 的 label selector？有没有和金丝雀发布结合？
- 有没有遇到"CI 过了但上线炸了"的情况？根因是什么，后来怎么加固的？
- 你们的 Docker 镜像是怎么做分层优化的？基础镜像是什么？编译和运行环境怎么分离？

**评分标准**：
- 只答"用 Jenkins/GitLab CI 自动部署" → 浅
- 能描述完整的发布流程和关键卡点 → 中
- 能从"CI 通过 ≠ 质量保证"出发，说明质量内建的策略和灰度/回滚机制 → 深

**优秀回答参考**：

> 这道题考的不是"用了什么工具"，而是"整个交付流程中有哪些防护层，每个防护层挡过什么事故"。

**第一层：完整的流水线设计。** 期望的结构是：Push → 编译/单元测试 → 代码扫描（SonarQube）→ 构建镜像 → 部署到 DEV 环境 → 集成测试 → (MR Review + 合并) → 部署到 STAGING（预发布环境）→ 冒烟测试 / 回归测试 → 灰度发布（到生产 5%→20%→100%）→ 监控观察 → 全量上线。每个环节都要有卡点（质量门禁），不满足条件不能进入下一阶段。比如 SonarQube 的 Quality Gate：新增代码覆盖率低于 80%、或新增阻断级 bug > 0，流水线直接失败。

**第二层：CI 通过 ≠ 上线安全。** 这才是深度的体现。CI 能保证的是"代码编译通过 + 单元测试通过"，但线上炸的原因多不在 CI 覆盖范围内：(1) 配置不一致（DEV 和 PROD 的数据库连接数不同、超时配置不同）；(2) 数据差异（PROD 的千万级数据和 DEV 的十万级走不同的执行计划）；(3) 第三方依赖（消息队列积压、缓存热点）。加固手段：STAGING 环境尽可能接近生产（至少相同规格的数据库实例、接近的数据量），冒烟测试不仅测功能、还要测关键接口的 RT 阈值，灰度阶段做 A/B 对比——切流 5% 后对比新旧版本的错误率和 RT，一经发现劣化立刻自动回滚。期望候选人能举一个"上线炸了之后在流水线里加了一个检查"的具体故事。

**第三层：Docker 镜像分层优化。** 多阶段构建（multi-stage build）是标准答案：第一阶段用完整的 JDK + Maven 编译，产物是一个 fat jar；第二阶段只复制 jar 到运行时镜像（`eclipse-temurin:17-jre-alpine` 或 `distroless`），这样最终镜像不包含编译工具和中间产物。分层技巧：把变化频率低的依赖放在前面，变化频率高的代码放在后面——利用 Docker 构建缓存加速。如果候选人额外提到把公共基础层（如公司统一的 JVM 调优脚本、时区配置）抽成 base 镜像统一维护，说明有实际的大规模运维经验。

**第四层：灰度发布的具体实现。** 如果用 K8s，最简洁的方式是：新老两个 Deployment，Service 的 selector 用 version label 控制权重。更成熟的用 Istio/Envoy 做流量分割 + Header 染色（特定用户路由到特定版本）。关键是灰度期间的观测——不是等用户投诉，而是主动看：错误率、RT P99、业务指标（如下单量）有没有下跌。

你管理过 50 人全功能团队，实施了 KPI/KPA/OKR 等多种考核方式。

**主问题**：你提到在团队中实施过 KPI、KPA、OKR 三种考核方式——分别在什么阶段、为什么切换？你认为对于不同角色（后端、前端、客户端、测试），考核方式应该有什么区别？有没有遇到过"考核导致行为走偏"的情况？

**追问方向**：
- OKR 在研发团队的实施最大的阻力是什么？你怎么让产品/测试也能参与进来？
- 你说"分管产品技术"，产品和研发的矛盾你怎么协调？有没有具体案例？
- 有没有开掉过人？原因是什么？你怎么判断一个人是"能力问题"还是"意愿问题"？

**评分标准**：
- 只答"因团队而异"或泛泛而谈 → 浅
- 能说出每种考核的具体适用场景和切换原因 → 中
- 能从真实案例出发，展现"考核-行为-结果"的闭环思考，并有纠偏经验 → 深

**优秀回答参考**：

> 这道题的核心在于"管理的本质不是考核，而是通过考核引导行为"。期望的回答应该展现出管理实践的迭代和反思。

**第一层：考核方式的演进逻辑。** KPI 适合目标明确、可量化的阶段（如交付速度、代码质量、线上事故率），但问题是：研发工作中有大量"重要但不紧急"的事情（技术债清理、文档建设、知识分享），KPI 量化不了，量化了就容易造假。KPA（Key Performance Area）弥补了 KPI 只关注结果的问题——它回到"关键绩效领域"，比如"代码质量"、"技术创新"、"团队协作"等，适合对产出多样性高的团队。OKR 则在公司战略层面对齐——但它需要自上而下的推行和透明开放的文化。期望的演进：初创期用 KPI 保证基本交付；团队扩大到 30+ 人后引入 KPA 覆盖软性指标；有明确公司战略目标后用 OKR 做目标对齐。三种不是互斥的——KPI 管底线，OKR 管上线，KPA 管过程。

**第二层：不同角色的差异化考核。** 后端看重稳定性（事故率、RT 稳定性、数据库慢查询减少率），客户端看重用户体验（崩溃率、启动时间、App Store 评分），测试不能单看 Bug 数（Bug 数一考核，测试就不愿意报小 Bug、也不愿意和开发协作），而应该看"线上逃逸 Bug 率"和"用例覆盖率增长"。这是一个信号：候选人是否能根据角色特点定制考核，而非一个模板套所有人。

**第三层：考核走偏的真实案例。** 把"代码提交次数"作为 KPI → 开发者拆分提交刷数据。把"Bug 修复速度"作为 KPI → 开发修 Bug 时不做根因分析，打个补丁就关。把"测试测出的 Bug 数"作为 KPI → 测试专挑界面文案这种小 Bug，核心逻辑反而没人测。好的管理者在发现走偏后，不是放弃考核，而是调整指标维度——比如从"提交次数"改为"需求交付周期（Lead Time）+ 线上事故率"的组合。这个"发现问题 → 复盘 → 调整"的闭环，是好管理者的标志。

**第四层：开掉人的决策框架。** 期望候选人有一套自己的判断标准，而不是说"因人而异"的空话。一个好的框架是：意愿+能力的四象限。"有能力无意愿"先聊——是不是激励出了问题、是不是倦怠了；"有意愿无能力"给时间+资源培养；"既无能力又无意愿"果断处理（但通常是流程问题在先——怎么招进来的？）。最有经验的回答是："大多数我开掉的人，反思下来是我做 manager 的失败——要么面试时没筛好，要么入职后没给足够的指导。但如果给了明确的反馈和改善时间却没有变化，那就必须做决定，因为留着是对团队其他人的不公平。"

### 题 10：技术债与架构演进

**主问题**：你在畅唐网络对原有 SOA（webservice）做了向 .NET Core RESTful + Docker 的改造升级。这类架构升级必然涉及业务中断风险和技术债取舍。你是怎么说服业务方和上级接受这类"看不到业务价值"的技术改造的？有没有改造到一半发现行不通、被迫回退的情况？

**追问方向**：
- 你如何和老旧系统做兼容过渡？有没有用到绞杀者模式（Strangler Fig）？
- 你怎么平衡"业务需求压力"和"技术债偿还"的时间分配？团队内部怎么分工的？
- 你判断"这个技术债必须现在还"和"可以再拖一拖"的标准是什么？

**评分标准**：
- 只答"技术升级理所当然" → 浅（缺商业思维）
- 能说清推进策略和妥协方案 → 中
- 能从实际案例出发，展现"技术决策×商业权衡×团队执行力"的三维思考 → 深

**优秀回答参考**：

> 这道题考的不是技术能力，而是"怎么让技术投资被非技术决策者理解和买单"——这是总监级和架构师的核心差异。

**第一层：怎么说服业务方。** 不讲技术术语，讲业务影响。"从 webservice 迁移到 RESTful + Docker"要翻译成：(1) 部署时间从 2 小时降到 10 分钟（Docker 容器化），紧急修 Bug 不再让全公司等；(2) 系统容量翻倍不需要重买服务器（K8s 弹性伸缩），一年省 X 万硬件成本；(3) 新游戏接入中台的时间从 2 周降为 3 天（标准化的 RESTful API），游戏业务方是直接受益者。另外，不要一上来就要资源做大改造——先找一个低风险的模块做试点，跑通了拿数据说话。这是 engineering with business sense。

**第二层：绞杀者模式（Strangler Fig）的实际落地。** Martin Fowler 提出的这个模式听起来很美：新系统逐步替换旧系统的功能，直到旧系统被完全"绞杀"。但实际执行中的难点是：在一个请求生命周期中，新旧系统之间怎么做路由？几个实用方法：(1) 在网关层（Nginx/API Gateway）通过 URL 前缀把特定业务路由到新系统，其余走旧系统；(2) 数据库层面的双写+同步（Maxwell/Canal 把旧库变更同步到新库）；(3) 一段过渡期内新旧服务同时在线，等旧服务流量降为零再下线。如果候选人经历过"双写期间数据不一致"的阵痛并讲出怎么处理的，就是经历了完整的绞杀。

**第三层：技术债的优先级判断。** 一个好的框架：(1) 如果技术债在"安全/数据完整性"这个层次（如没有备份、没有访问控制、SQL 注入风险），必须立刻还，没得商量；(2) 如果技术债在"团队交付速度"这个层次（如每次发布需要手工操作、每次改一个模块连带改 10 个地方），按 20% 原则——每个 sprint 固定 20% 的时间还这类债，永远不为新需求放弃；(3) 如果技术债在"架构优雅"这个层次（如"这个设计不符合 DDD"，但不对业务和交付有实际影响），可以拖，甚至可以永远不还——因为过度设计也是一种债。好的技术管理者知道"有些技术债会利滚利（如没有自动化测试），有些永远不会（如用了一个不够时髦的框架但运行稳定）"。

**第四层：平衡业务需求和技术债的组织方案。** 团队分成"业务 stream"和"平台 stream"——业务 stream 主要承接业务需求，平台 stream 负责基础设施建设和技术债清理。但注意不能让两个团队完全隔离（平台团队会脱离业务痛点，造出没人用的轮子）。采用轮岗制——业务开发定期去平台团队轮换，把业务的痛带过去。这才是可执行的方案，而不是教科书式的"每周安排 20% 时间"。

### 题 11：POA 联盟链的工程实践（Bonus）

你在数字权益平台中基于以太坊搭建了 POA 联盟链。

**主问题**：你们选 POA 而不是 PBFT/Raft 的共识，是出于什么考虑？POA 的签名者在 4-7 个节点之间——你们怎么处理签名者节点的故障和替换？在联盟链场景下，你们为什么没用 Hyperledger Fabric 而是自建以太坊 POA 链？

**追问方向**：
- ERC20 和 ERC721 合约中你们有没有自定义扩展逻辑？合约升级是怎么做的（proxy pattern?）？
- Uniswap 合约你是自己部署的还是 Fork 的？有没有改动 AMM 曲线参数？
- 区块链的数据存储层（LevelDB）在大批量事件查询时性能如何？你们怎么优化的？

**评分标准**：
- 只答技术选型结论 → 浅
- 能说出 POA vs PBFT 在联盟链场景下的工程差异 → 中
- 能从共识故障恢复、合约可升级性、存储查询性能等完整链路说明 → 深

**优秀回答参考**：

> 区块链题作为 bonus，但能展现出候选人对"分布式系统共识"的深层理解——这是和前面分布式题联动的。

**第一层：POA vs PBFT 的工程选型。** POA（Proof of Authority）基于 Clique 共识，每一轮出块只有一个签名者参与，区块确认只需要单一签名验证，出块速度快（几秒一个块）。PBFT 需要三轮广播（Pre-prepare → Prepare → Commit），通信复杂度 O(n²)，节点数超过 7-10 个时性能急剧下降。联盟链场景下节点数量少且都是可信实体，POA 的性能远超 PBFT。但 POA 的弱点是：(1) 没有最终性（Finality）概念——块可能被重组（深度较浅时）；(2) 签名者故障时，如果剩余签名者数量小于 `floor(N/2)+1`，出块会停滞。PBFT 有即时最终性——一轮共识完成后区块不可逆。如果业务需要强最终性（如支付清算），PBFT 更合适。选型逻辑：如果业务能接受 6-12 个块的确认延迟（POA 的软最终性），POA 的吞吐和低延迟远超 PBFT。候选人能说清楚这两个的 trade-off 就行。

**第二层：签名者故障恢复的实际操作。** Clique 的签名者列表存在区块头的 extraData 字段里。替换签名者需要发起一次投票——当前多数签名者对一个 proposal（添加或移除签名者）投票赞成后生效。实际操作中最大的坑是：如果签名者数量减少到临界值（少于 `floor(N/2)+1`），没有足够节点投票，就无法添加新签名者——系统死锁。解法：提前配置高于最低阈值的初始签名者数量，或预留一个能随时通过硬分叉恢复的应急流程。

**第三层：为什么不用 Fabric。** Hyperledger Fabric 的功能更强（通道隔离、私有数据集合、可插拔共识），但运维复杂度是 Geth POA 链的数倍。Fabric 需要维护 CA、Orderer、Peer、CouchDB 等多个组件，且版本升级几乎必然有兼容性问题。对于一个中小型数字权益平台，Geth + POA 足够，团队没有 Fabric 运维能力的话强行上 Fabric 是过度设计。这个回答展现出"根据团队能力和业务需求选型"而非"选最先进的"。

**第四层：合约可升级性与链上数据查询。** ERC20/ERC721 扩展通常是对权限模型和资产属性的定制（如可暂停转账、黑白名单）。合约升级的 proxy 模式（OpenZeppelin 的 Transparent Proxy 或 UUPS）：逻辑合约和存储合约分离，通过 `delegatecall` 实现代码升级但保持数据不变。这里有个大坑——升级时必须保证新合约的存储布局和旧合约完全兼容（变量类型和顺序不能变），否则会读到错位的数据。LevelDB 查询慢的经典解法：链上只存事件哈希或最小必要数据，完整的业务数据写入链下的关系型数据库或 ES——通过监听合约事件（Event Log）同步到链下索引。这是区块链工程化的关键认知。
