## 二、背景与问题

项目已经具备斗地主发牌、拆牌、牌力评分、重洗过滤、Java/C++ 双实现、基准测试和线上算法模拟器，可以作为确定性的算法服务使用。

当前能力还不能直接称为完整的“斗地主发牌算法智能体”，主要原因如下：

- 用户目标还没有被统一转换为指标、约束、样本量和验收阈值。
- Java/C++ 实现存在已知正确性与一致性风险，可能污染后续调参结论。
- 现有测试入口不能稳定区分普通回归、性能测试和大样本模拟。
- 实验结果缺少统一的随机种子、配置版本、算法版本和对比基线记录。
- 模型、确定性算法和用户审批之间的职责边界尚未固化。
- 源仓、快照以及 `algorithm/native/previous/` 的修改与同步规则需要统一。

因此，本 Spec 将“算法服务”和“智能体编排”明确分层：算法代码负责确定性计算，智能体负责理解目标、编排工具、解释证据和推动审批。

## 三、目标与非目标

### 3.1 目标

- 将自然语言需求转换为可执行、可复现、可验收的算法任务契约。
- 在任何策略比较或参数调优前，建立发牌、评分和双实现一致性的核心不变量。
- 复用现有模拟器，用固定种子、配置版本和算法版本生成可追溯证据。
- 支持正确性排查、策略比较、参数调优、公平性评估、性能评估和版本同步。
- 所有代码或配置修改均由用户确认后实施，并自动触发相应回归检查。
- 在执行入口和产物格式稳定后，用 project skill 固化交互流程。

### 3.2 非目标

- 不构建通用多智能体平台、通用实验平台或新的工作流引擎。
- 不让模型实现牌型识别、牌力计算、随机发牌、统计聚合或随机数生成。
- 不把启发式牌力分数描述成真实胜率或玩家体验的充分证明。
- 不默认扩展到叫分、出牌决策、自对弈或强化学习。
- 不为了未来扩展新增抽象层、第三方依赖或重复模拟器。
- 不允许智能体绕过用户审批直接修改线上配置或同步线上参照代码。

## 四、设计原则

1. **确定性内核**：牌型、拆牌、评分、发牌、随机数和统计计算由代码完成，模型不得替代计算。
2. **正确性先于优化**：核心不变量未通过时，不开展参数调优、公平性结论或性能优化。
3. **复用现有入口**：优先使用 `algorithm/native/extracted/harness.cpp`、现有 Java 测试和现有统计脚本，不创建第二套模拟体系。
4. **实验可复现**：每个结论记录算法版本、配置版本、随机种子、样本量、命令和指标口径。
5. **双实现对齐**：同时涉及 Java 与 C++ 的规则和修复必须使用共享向量或等价输入验证可观察结果。
6. **结论有边界**：静态牌力、模拟分布和线上胜率是不同证据，不得互相替代。
7. **修改需审批**：智能体可以生成候选方案和补丁建议，但代码、配置和线上同步须经用户确认。
8. **严格同步边界**：仓库规则冲突未消除前，采用更严格的源仓修改、快照同步规则。

## 五、系统边界

### 5.1 模型负责

- 识别任务属于正确性、策略、调参、公平性、性能或同步中的哪一类。
- 澄清业务目标，将模糊诉求转换为指标、约束和验收条件。
- 选择并编排现有确定性工具，形成最小实验方案。
- 比较基线与候选结果，解释证据、风险、限制和建议。
- 在修改前请求用户确认，并在修改后汇总回归结果。

### 5.2 代码与工具负责

- 验证牌的完整性、唯一性、张数和座位分配。
- 识别牌型、拆牌、计算牌力和重洗判定。
- 使用明确的随机种子生成牌局。
- 执行样本聚合、分位数、比例、耗时和差异计算。
- 执行 Java/C++ 回归、共享测试向量和性能检查。
- 以非零退出码或明确失败结果阻止错误结论继续传播。

### 5.3 用户负责

- 确认业务目标、指标权重、可接受阈值和适用房间。
- 决定是否采纳候选参数、配置或算法修改。
- 批准源仓修改、快照同步和线上参照更新。
- 对产品体验、公平性边界和上线风险作最终判断。

## 六、任务类型

智能体首先将请求归入以下类型；目标或验收条件不明确时，先澄清，不运行大样本模拟。

| 类型 | 典型输入 | 默认动作 | 是否允许自动修改 |
| ---- | ---- | ---- | ---- |
| 正确性排查 | 分数不一致、牌数异常、Java/C++ 结果不同 | 最小复现与回归测试 | 否 |
| 策略比较 | 比较两种拆牌或发牌策略 | 同输入、同种子对比 | 否 |
| 参数调优 | 调整阈值、重洗次数或配置组合 | 基线采样与候选扫描 | 否 |
| 公平性评估 | 比较座位、房间或玩家类型分布 | 分层统计与不确定性说明 | 否 |
| 性能评估 | 评估耗时、吞吐或重洗成本 | 独立 benchmark | 否 |
| 版本同步 | 将源仓实现同步到分析仓快照 | 检查来源、版本和差异 | 否 |

## 七、核心不变量

以下不变量是所有后续实验的前置门槛。

| 不变量 | 验证要求 | 失败行为 |
| ---- | ---- | ---- |
| 牌组完整 | 每局共 54 张且无重复、无缺失 | 立即失败 |
| 发牌张数 | 三家各 17 张，底牌 3 张 | 立即失败 |
| 返回分数一致 | 返回结果中的三家分数必须等于对返回手牌重新计算的分数 | 立即失败 |
| Combo 长度一致 | `Combo.length` 必须等于该组合实际消耗的牌数 | 立即失败 |
| 重洗有界 | 重洗次数不得超过配置上限，达到上限后返回值仍须完整评估 | 立即失败 |
| 固定输入可复现 | 相同版本、配置和种子得到相同可观察结果 | 阻止对比结论 |
| Java/C++ 口径一致 | 共享向量覆盖的牌型、长度和分数结果一致 | 阻止双实现发布 |
| 测试真实执行 | C++ Release 构建不能因 `NDEBUG` 跳过断言，CTest 能发现测试 | 阻止验收 |
| 测试分层 | Java 默认测试不运行 benchmark，benchmark profile 明确运行 | 阻止性能结论 |

Java 与 C++ 随机数实现可以不同，因此“双实现一致”默认指共享确定性输入下的牌型、组合长度、牌力和过滤判定一致，不要求两端用同一种子生成完全相同的牌序。若任务要求牌序逐局一致，必须单独定义随机数协议。

## 八、任务契约

执行前形成最小任务契约，至少包含：

- 业务目标及不能接受的结果。
- 任务类型和目标实现：Java、C++、线上模拟器或多端对比。
- 房间、玩家构成、策略和配置版本。
- 主要指标、保护指标及各自阈值。
- 样本量、随机种子或种子范围。
- 基线版本和候选版本。
- 允许的执行时间与性能预算。
- 期望产物：复现记录、比较报告、候选配置或补丁建议。

“优化体验”“更公平”“减少差牌”等输入不能直接进入调参。模型必须先将其转成可计算指标，例如极端分位数、座位差异、重洗率、手数分布或耗时上限，并明确这些指标只是业务目标的代理变量。

## 九、端到端流程

### 9.1 分类与澄清

1. 确认任务类型、作用范围和目标实现。
2. 补齐会改变实验结论的业务条件。
3. 形成任务契约并请用户确认关键指标与阈值。

### 9.2 读取最小上下文

按任务需要读取以下内容，不无差别加载全部算法文件：

1. `algorithm/docs/rules.md` 与相关产品或算法 PRD。
2. 目标 Java/C++ 实现及其全部调用方。
3. 对应测试、配置与模拟入口。
4. `docs/knowledge/makedeal-simulation.md` 等指标口径文档。
5. 与目标房间或策略直接相关的历史结论。

### 9.3 前置正确性验证

- 运行与任务相关的单元测试和核心不变量检查。
- 涉及双实现时运行共享向量或等价输入对比。
- 涉及线上逻辑时确认使用的是 `algorithm/native/extracted/` 中的线上模拟器，而不是方向性近似实现。
- 任一前置检查失败时，任务转为正确性排查，不继续大样本调优。

### 9.4 建立基线

- 固定算法版本、配置版本、命令、样本量和种子。
- 运行当前策略，保存聚合指标和失败样本。
- 检查样本量与指标波动是否足以支持后续比较。
- 历史基线只有在评分公式、拆牌策略和指标口径均未变化时才能复用。

### 9.5 运行候选实验

- 基线与候选使用相同的房间、玩家构成、样本量和种子集合。
- 一次实验只改变任务契约中声明的因素。
- 扫描已有稳定脚本能表达的参数组合，不新增通用调参框架。
- 记录无效牌局、程序错误、超时和达到重洗上限的次数。

### 9.6 解释与决策

智能体输出以下内容：

- 候选方案相对基线的主要指标变化。
- 保护指标是否退化。
- 样本量、波动和不能证明的事项。
- 推荐方案、风险和精确复现命令。
- 需要用户确认的配置或代码修改。

只有用户确认后，才能修改源代码、配置或同步快照。

### 9.7 修改与回归

- 正确性缺陷优先在所有调用方共享的根因位置修复。
- 同一规则存在 Java/C++ 实现时，修复和测试范围必须覆盖两端。
- 参数变化必须重新运行对应分布基线和保护指标。
- 性能测试独立运行，不混入日常单元测试。
- 变更完成后记录源仓 commit、快照 commit、配置版本和验证结果。

## 十、实验输入与产物

### 10.1 最小实验输入

| 字段 | 要求 |
| ---- | ---- |
| `task_type` | 正确性、策略、调参、公平性、性能或同步 |
| `algorithm_version` | 源仓 commit 或可定位版本 |
| `snapshot_version` | 分析仓 `algorithm/` 快照 commit |
| `config_version` | 配置文件摘要或显式版本号 |
| `target` | Java、C++ harness 或两者 |
| `room` | 房间或策略作用域 |
| `player_mix` | 真人与机器人构成 |
| `sample_size` | 每组有效牌局数 |
| `seed` | 单个种子或明确范围 |
| `metrics` | 主指标、保护指标及口径 |
| `command` | 可复制的执行命令 |

### 10.2 最小实验输出

- 有效牌局数、无效牌局数和失败原因。
- 发牌完整性与重洗上限检查结果。
- 三家牌力、极差、潜在地主牌力和地主优势的分布。
- 单牌数、炸弹数、最优手数等结构指标。
- 按座位、房间和玩家类型分层的指标。
- 重洗率、平均重洗次数和达到上限的比例。
- 总耗时、单局耗时或吞吐量。
- 基线与候选的绝对差、相对差和样本量。
- 算法版本、配置版本、种子与复现命令。

### 10.3 产物保存

- 算法规则、测试说明和稳定的工具用法继续保存在 `algorithm/docs/`。
- 可再生的大体量 JSONL 保持在已有忽略规则覆盖的位置，不提交仓库。
- 房间策略的持久分析结论沿用 `docs/makedeal-strategies/`。
- 智能体设计规范保存在 `docs/spec/`，实施计划保存在 `docs/plan/`。
- 不为单次实验新建通用目录、数据库或产物注册中心。

## 十一、公平性与统计解释

- 公平性评估至少按座位、房间、策略版本和玩家构成分层。
- 比较结论必须同时报告样本量与差异，样本不足时只报告观察，不下稳定性结论。
- 同种子配对比较优先于两组独立随机样本，以减少随机波动。
- 静态牌力只能用于评估发牌结构；若要声称胜率或体验改善，必须引入真实牌谱或经过确认的对局模拟证据。
- 多指标扫描可能产生偶然最优候选，最终方案必须在独立种子范围上复验。
- 阈值或评分公式变化后，旧分位数基线自动失效，必须重新采样。

首版不强制引入新的统计库。现有脚本能稳定计算的计数、均值、分位数和配对差异足以支持初筛；只有业务决策明确需要置信区间或显著性检验时，才在现有脚本中增加最小实现。

## 十二、失败处理

| 失败阶段 | 行为 | 是否继续 |
| ---- | ---- | ---- |
| 目标或指标不明确 | 请求用户确认关键歧义 | 否 |
| 核心不变量失败 | 保存最小复现，转为正确性修复 | 否 |
| Java/C++ 共享向量不一致 | 输出首个差异及两端版本 | 否 |
| 固定输入不可复现 | 检查种子、配置和版本记录 | 否 |
| 模拟器异常或无效牌局 | 记录错误并返回非零状态 | 否 |
| 样本量不足 | 报告观察与缺口，不给调参结论 | 否 |
| 保护指标退化 | 标记候选不通过 | 否 |
| 性能超过预算 | 报告瓶颈和基线差异 | 否 |
| 源仓或快照来源不清 | 停止修改与同步 | 否 |

失败样本必须保留足以复现问题的种子、配置和版本信息；不得仅保存自然语言描述。

## 十三、仓库所有权与同步规则

当前仓库存在两条不同强度的规则：

- 项目协作指南表示 `algorithm/` 中 Java/C++ 实现可改，`algorithm/native/previous/` 是需同步记录的线上参照副本。
- `algorithm/README.md` 将整个 `algorithm/` 定义为源仓的只读快照，要求所有改动先进入源仓再同步。

在两者统一前，本 Spec 采用更严格且更安全的规则：

1. `algorithm/` 默认视为只读快照，不直接作为算法修复的权威提交位置。
2. 算法代码修改先在源仓完成并验证，再同步到本仓库。
3. 同步时记录源仓 URL、源 commit、同步日期和分析仓 commit。
4. `algorithm/native/previous/` 继续视为线上代码参照副本，不得静默修改。
5. 若必须修复 harness 自身引入的问题，应明确标注其与线上代码的偏差及对既有基线的影响。
6. 若项目决定允许直接修改 `algorithm/`，必须先统一更新 `algorithm/README.md`、项目协作指南和本 Spec。

## 十四、Skill 设计

### 14.1 创建时机

满足以下条件后创建 project skill：

- 核心不变量和已知正确性问题已经修复并通过回归。
- 固定种子、配置和版本的模拟入口稳定。
- Java/C++ 共享向量或等价验证入口稳定。
- 至少完成 5 个真实任务，证明任务契约和产物格式没有频繁变化。

### 14.2 Skill 最小职责

拟使用名称：`dealing-algorithm-agent`。

Skill 只编排以下稳定流程：

1. 分类任务并形成最小任务契约。
2. 读取目标实现、调用方、规则、测试和指标口径。
3. 运行核心不变量与双实现检查。
4. 使用固定版本、配置和种子运行现有模拟工具。
5. 比较基线与候选，输出证据、风险和复现命令。
6. 在修改前请求用户批准，并在修改后运行相应回归。
7. 提醒源仓、快照及 `native/previous/` 的同步要求。

### 14.3 Skill 禁止承载

- 牌型识别、拆牌、评分、洗牌和统计计算实现。
- 算法权重、房间配置和阈值的复制文本。
- 替代真实测试的自然语言正确性判断。
- 未经批准修改配置、算法或线上参照副本的指令。
- 为不稳定入口创建的兼容层或通用包装器。

首版只创建 `.agents/skills/dealing-algorithm-agent/SKILL.md`，引用现有规范、测试和模拟器，不增加新脚本。只有稳定流程仍需要重复手工拼接命令并造成实际错误时，才增加窄职责包装脚本。

## 十五、分阶段交付

### 阶段 A：正确性与测试基础

- 修复重洗返回值与分数不一致问题。
- 修复连对 `Combo.length` 口径。
- 清理或明确 C++ 注入构造函数的生命周期所有权。
- 为 Java benchmark 补齐有效标签。
- 为 C++ 增加 CTest 注册和不受 `NDEBUG` 影响的断言。
- 建立返回分数重算、牌组完整、重洗上限和连对长度测试。

**完成定义**：Java 与 C++ 的核心不变量测试全部通过，普通测试、benchmark 和 CTest 的入口可以分别执行。

### 阶段 B：可复现实验与评估

- 固化种子、配置、版本、样本量和命令记录。
- 建立 Java/C++ 共享向量或等价验证数据。
- 用现有 harness 完成同种子基线与候选比较。
- 固化正确性、分布、公平性和性能的最小输出字段。

**完成定义**：同一实验可以按记录重跑，基线与候选差异可定位到版本、配置和种子。

### 阶段 C：智能体闭环

- 固化任务分类和任务契约。
- 将模糊业务目标转换为经用户确认的指标与保护条件。
- 形成模拟、解释、审批、修改和回归闭环。
- 选取至少 5 个真实任务作为回归案例。

**完成定义**：智能体不会在不变量失败、样本不足或未经审批时给出可上线修改。

### 阶段 D：Project Skill

- 创建最小 `dealing-algorithm-agent` skill。
- 引用现有代码、规范和工具，不复制确定性算法。
- 用阶段 C 的真实任务验证触发、流程和输出。

**完成定义**：Skill 能稳定编排已有能力；移除 Skill 后，算法正确性和测试保护仍然成立。

## 十六、验收标准

### 16.1 功能验收

- 能将请求归类为六种任务类型之一并形成完整任务契约。
- 能基于相同种子和配置比较基线与候选策略。
- 能输出候选方案、保护指标、风险、版本和复现命令。
- 能在获得用户确认后进入修改，并自动选择对应回归范围。
- 能将稳定结论保存到既有文档目录而不创建重复体系。

### 16.2 正确性验收

- 每局满足 54 张唯一牌和 17/17/17/3 分配。
- 重洗返回的分数与返回手牌重算结果完全一致。
- 三连对等组合的长度等于实际牌数。
- 重洗次数不超过配置上限，极端配置也能终止。
- Java/C++ 共享向量覆盖的可观察结果一致。

### 16.3 可复现性验收

- 每个实验记录算法版本、快照版本、配置、种子、样本量和命令。
- 相同输入可以重现相同结果；不能重现时任务失败。
- 评分或拆牌逻辑变化后，不复用旧分位数基线。
- 候选方案在独立种子范围上复验后才能推荐。

### 16.4 测试与性能验收

- Java 默认测试不运行 benchmark，benchmark profile 明确运行全部目标用例。
- CMake 注册测试，CTest 能发现并执行；Release 构建仍能识别失败。
- 正确性回归与性能测试分开运行和报告。
- 性能变化同时报告基线、样本量和运行环境。

### 16.5 安全与同步验收

- 未经用户确认不修改算法、配置或线上参照副本。
- 每次快照同步能追溯到源仓 commit。
- `algorithm/native/previous/` 的任何变化都有明确原因、同步来源和影响记录。
- 仓库规则冲突解决前，所有算法实现修改遵循更严格的只读快照边界。

## 十七、实施约束

- 优先修复共享根因，不在多个调用方重复增加保护。
- 优先复用现有 harness、测试和统计脚本，不新增通用框架。
- 首阶段只处理审查中已确认的正确性和测试入口问题，不顺手重构领域模型。
- `Card` 冗余方法和接口重复声明仅在触及同一文件且能减少代码时顺带清理，不单独立项。
- 本 Spec 通过评审后再编写实施计划，不直接以章节顺序代替开发任务拆解。
