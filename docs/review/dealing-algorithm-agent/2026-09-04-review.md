# 斗地主发牌算法智能体审查（2026-09-04）

## 方向定义

当前实现覆盖牌型拆分、牌力评分、发牌、重洗、Java/C++ 双实现和性能测试，属于较完整的斗地主发牌算法服务。

若要称为智能体，还需要加入“理解目标与约束、选择或调整策略、调用仿真、解释结果、根据反馈继续迭代”的任务闭环。算法本身仍应保持确定性，模型只负责目标理解、工具编排和结果解释。

## 审查发现

### P1-1 Java 和 C++ 重洗结果可能携带上一局分数

**证据**：Java 在 `algorithm/src/main/java/com/mamba/landlord/algorithm/shuffle/strategy/DefaultReshuffleDealStrategy.java:114-125` 生成新牌面后，快速失败分支保留旧 `seatScores`；达到最大次数后，`DefaultReshuffleDealStrategy.java:136-137` 用新 `dealData` 和旧分数构造结果。C++ 在 `algorithm/native/include/landlord.h:1168-1178,1187-1195` 存在相同逻辑。

**影响**：返回的 `handStrength`、EHS 与实际手牌不对应，污染日志、离线标定和下游判断。

**建议**：删除收益未经证明的快速失败，始终对新牌面全量评估，并增加“返回分数等于对返回手牌重算分数”的测试。

### P2-1 `Combo.length()` 对连对少算一半

**证据**：Java `algorithm/src/main/java/com/mamba/landlord/core/model/Combo.java:119-134` 与 C++ `algorithm/native/include/landlord.h:232-247` 都让 `CONSECUTIVE_PAIRS` 返回 `mainRanks.size()`，正确牌数应为 `mainRanks.size() * 2`。

**影响**：当前生产路径未调用该方法，但公开模型 API 返回错误，后续统计或规则代码复用时会出错。

**建议**：同步修改两套实现，并各增加“三连对长度等于 6”的断言。

### P2-2 benchmark profile 配置无效

**证据**：`algorithm/pom.xml:88-115` 默认排除 `benchmark` 分组；两个 benchmark 类没有 `@Tag("benchmark")`。普通 `./mvnw test` 实际执行了 8 项 benchmark，包括 100,000 局采样。

**影响**：默认测试混入非确定性性能测试，耗时与输出会随 benchmark 规模增长。

**建议**：给两个 benchmark 类增加 `@Tag("benchmark")`，继续复用现有 Surefire 配置。

### P2-3 C++ 测试未接入 CTest

**证据**：`algorithm/native/CMakeLists.txt:13-18` 只创建可执行文件，没有 `enable_testing()` 或 `add_test()`；`algorithm/native/test/main_test.cpp:9-297` 全部依赖标准 `assert`。

**影响**：`ctest` 无法发现测试；Release 构建定义 `NDEBUG` 后会移除断言，却仍可打印 `All tests passed`。

**建议**：在 CMake 注册现有测试，并让断言不依赖 `NDEBUG`；无需引入新测试框架。

### P2-4 C++ 注入构造函数保留外部对象指针

**证据**：`algorithm/native/include/landlord.h:995-1028` 的 `DefaultComboExtractor` 保存 scorer 裸指针；`landlord.h:1040-1042` 复制成员时，extractor 仍指向调用方对象。当前仓库未调用该构造函数。

**影响**：调用方 scorer 生命周期结束后会产生悬空指针；内部 scorer 与 extractor scorer 也可能配置不一致。

**建议**：删除当前未使用的构造函数。确有注入需求时，只接收 scorer，并用内部 `handScorer_` 初始化 extractor。

## 缺失能力规划

### 第一阶段：守住算法不变量

| 缺失能力 | 最小落地点 | 验收标准 |
| ---- | ---- | ---- |
| 返回状态一致性 | 对最终牌面重新计算派生分数 | 任意返回结果重算后完全一致 |
| Java/C++ 对齐 | 共用测试向量与结果比对 | 同输入下关键牌型、评分和策略结果一致 |
| 发牌合法性 | 校验 54 张牌唯一、座位牌数和底牌数 | 随机样本中无重复、遗漏或牌数错误 |
| 测试入口可靠 | Maven 隔离 benchmark，CMake 注册测试 | 默认测试稳定，性能测试显式运行 |

### 第二阶段：补齐可评估的策略工具

| 缺失能力 | 建议实现 | 验收标准 |
| ---- | ---- | ---- |
| 可复现实验 | 所有仿真接受并记录随机种子、配置和版本 | 任一异常样本可复现 |
| 策略比较 | 同一批牌局比较不同参数或策略 | 输出胜率代理、牌力分布、重洗率和耗时 |
| 公平性评估 | 按座位、房间和配置检查分布偏差 | 报告样本量、置信范围和异常阈值 |
| 边界样本库 | 保存炸弹、火箭、极端弱牌和重洗上限样本 | Java/C++ 回归共同覆盖 |
| 性能基线 | benchmark 单独执行并保存关键指标 | 算法修改可识别显著性能退化 |

### 第三阶段：形成算法智能体闭环

- 接收业务目标，例如降低极端牌局、控制重洗率或比较参数，不直接接受含糊的“优化体验”。
- 将目标转换为明确指标和约束，选择已有仿真工具执行，不让模型自行计算牌型或分数。
- 输出候选配置、证据、风险和可复现实验命令，由用户决定是否采用。
- 用户批准后才修改配置或代码，并自动执行双语言回归与性能验证。
- `algorithm/native/previous/` 继续作为线上参照副本；任何修改都必须同步线上并记录，不由智能体静默覆盖。

## Dealing Algorithm Skill 建议

建议创建，但应先形成一个稳定、可传入 seed 和配置的仿真入口。没有确定性工具入口时，skill 只能描述人工步骤，收益有限。

最小职责：

1. 区分规则正确性、评分调参、发牌策略、性能和线上同步任务。
2. 修改前读取 Java、C++ 对应实现和所有调用方，明确双实现是否都在范围内。
3. 把业务目标转换为可量化指标、约束和仿真样本量。
4. 调用确定性测试和仿真工具，记录 seed、配置、版本与结果。
5. 修改后检查牌面与派生分数一致性，并比较 Java/C++ 结果。
6. 涉及 `native/previous/` 时提示线上同步与变更记录要求。

不应放入 skill 的内容：牌型识别、评分公式、随机算法和统计计算。这些必须由可测试代码完成，skill 只编排与审阅。

首版同样只需一个 `SKILL.md`，引用算法设计、测试命令和同步规则。等仿真流程出现稳定重复参数后，再考虑增加包装脚本。
