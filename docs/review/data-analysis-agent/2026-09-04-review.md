# AI 数据分析智能体审查（2026-09-04）

## 方向定义

该方向负责把自然语言分析问题转换为可验证的数据结论，完整链路应为：问题澄清、指标口径匹配、SQL 生成、安全检查、查询执行、结果质检、分析解释和产物留档。

当前项目已经具备数仓知识、SQL 规范、分析文档、查询工具和批量回填脚本，但执行安全与结果验证仍不足，尚未形成可靠的智能体闭环。

## 审查发现

### P0-1 回填把零行结果误判为成功

**证据**：`ops/py/sr_exec.py:8-17,139-143` 说明 CloudBeaver 会吞掉 StarRocks strict mode 回滚，必须在写入后复核；`ops/py/backfill_runner.py:120-134` 无论 `COUNT` 是否为 0 都增加 `success`；`ops/py/daily_backfill.py:151-159` 与 `ops/py/daily_retention.py:147-153` 继续把零行标记为 `OK`。

**影响**：INSERT 静默回滚时仍以退出码 0 报告成功。此前已经执行 DELETE，目标日期可能为空，下游任务仍会继续计算。

**建议**：在 `run_backfill` 内校验行数，默认要求 `rows > 0`；确实允许空结果的任务显式声明 `allow_zero`。失败时抛错并阻止下游执行，不解析人类可读日志判断成功。

### P1-1 DELETE 与 INSERT 缺少原子性或恢复策略

**证据**：`ops/py/backfill_runner.py:113-140` 依次执行独立的 DELETE、INSERT、COUNT，失败后没有事务、暂存、备份或补偿。该函数被 20 个 `batch_insert_*.py` 脚本调用。

**影响**：网络失败、SQL 错误或 strict mode 回滚会让目标日期为空，失败窗口内查询可能读取损坏分区。

**建议**：先验证当前 StarRocks/CloudBeaver 链路是否支持同会话事务。若不支持，采用“写暂存并校验后替换”，或至少重试 INSERT 并阻止所有下游任务。修复应位于公共执行器，不分散到 20 个调用方。

### P1-2 查询工具没有执行 DDL 禁令

**证据**：`AGENTS.md:13` 与 `SQL_STYLE.md:5` 禁止脚本执行 DDL；`ops/py/sr_exec.py:224-246` 未检查 SQL 类型，命令行、文件和标准输入都会直接提交。

**影响**：项目最重要的数据安全红线只存在于文档，误传 `CREATE`、`ALTER`、`DROP` 或 `TRUNCATE` 语句时会直接执行。

**建议**：在唯一执行入口去除前导注释后检查首个关键字，保守拒绝 DDL 并提示用户在 CloudBeaver 手动执行。无需引入完整 SQL parser。

### P2-1 SQL 未统一执行防零除规范

**证据**：`AGENTS.md:18` 与 `SQL_STYLE.md:153-156` 要求分母使用 `NULLIF`。`ops/py/batch_insert_allgame_stat.py:54-55,114-115`、`ops/py/batch_insert_app_silvergame_stat.py:86-87`、`docs/analysis/plan/retention/retention-financial.md:535-541` 和 `docs/analysis/plan/retention/retention-score-game.md:60-68,133-139` 存在直接除法。

**影响**：可选 cohort、LEFT JOIN 基数或 `start_money=0` 时可能报错或产生不一致结果，并继续复制错误模板。

**建议**：先修可能为 0 的字段分母，再机械统一百分比表达式为 `NULLIF(denominator, 0)`。

## 缺失能力规划

### 第一阶段：建立可信执行闭环

| 缺失能力 | 最小落地点 | 验收标准 |
| ---- | ---- | ---- |
| SQL 执行安全 | `sr_exec.py` 拦截 DDL、限制多语句并清晰报错 | 危险语句无法由脚本提交 |
| 写入结果验证 | 公共回填器支持行数与业务断言 | 零行或异常写入返回非零退出码 |
| 失败可恢复 | 明确事务、暂存替换或补偿策略 | DELETE 后失败不会静默留下空分区 |
| 凭据隔离 | 环境变量或本地私密配置 | 仓库和日志不包含可重放凭据 |

### 第二阶段：补齐分析智能体流程

| 缺失能力 | 建议实现 | 验收标准 |
| ---- | ---- | ---- |
| 问题澄清 | 输出指标、时间范围、粒度、过滤条件和对照组 | SQL 执行前口径可被用户确认 |
| 知识检索 | 优先读取 `docs/knowledge/`、`SQL_STYLE.md` 和相关案例 | 不用底分反推房间，不默认回退 raw |
| SQL 静态检查 | 检查分区过滤、DWS 优先、别名、去重和防零除 | 常见红线在执行前被阻断 |
| 结果质检 | 校验空值、样本量、分母、时间覆盖和异常波动 | 结论附带质检状态与限制 |
| 结论溯源 | 保存问题、SQL、口径、结果摘要与生成时间 | 任一结论可回到实际执行 SQL |

### 第三阶段：形成评估与反馈闭环

- 建立少量真实分析任务作为回归集，检查 SQL 可执行性、口径正确性和结论一致性。
- 记录用户对口径和结论的修正，更新知识文档，不把临时偏好写进通用提示词。
- 仅在重复查询成本真实出现后增加查询缓存、语义层或复杂任务编排。

## Data Analysis Skill 建议

建议创建，但应等第一阶段安全问题修复后再落地，否则 skill 会把不安全流程自动化。

最小职责：

1. 判断任务是临时查询、分析方案、结果解释还是数据回填。
2. 按项目优先级读取知识文档和既有分析案例。
3. 生成 SQL，并在执行前逐项检查项目红线。
4. 只通过 `ops/py/sr_exec.py` 查询；DDL 明确转交用户手动执行。
5. 对结果做最小质检，再生成包含口径、证据和限制的分析结论。
6. 将临时 SQL 放入 `ops/py/tmp/`，需要留存的结论写入既有分析目录。

不应放入 skill 的内容：数据库凭据、表结构副本、SQL parser、业务指标硬编码和重试实现。这些分别属于私密配置、知识文档与确定性代码。

首版只需要一个 `SKILL.md` 引用现有规范，不创建额外脚本。连续完成 5 至 10 个真实分析任务后，再根据重复失败点决定是否增加检查脚本。
