## 方向定义

项目基础设施为数据分析和发牌算法提供共享的安全、构建、测试、规范和可观测能力。它不是第三个业务智能体，不需要独立的智能体对话入口。

## 审查发现

### P0-1 CloudBeaver 凭据被提交且通过明文 HTTP 发送

**证据**：`ops/py/sr_exec.py:23-26` 固定写入 HTTP 地址、用户名和密码摘要；`sr_exec.py:43` 直接向该地址发送请求；`sr_exec.py:55-60` 把凭据放入认证请求。

**影响**：仓库读者可能获得可重放认证材料；HTTP 链路上的凭据、查询和结果可能被监听或篡改。MD5 摘要在此处仍是登录凭据，不是安全脱敏。

**建议**：立即轮换账号凭据；从环境变量或不入库的本地配置读取 endpoint、user 和 credential，缺失时明确失败。服务支持时改用 HTTPS；若只能走受限内网 HTTP，应限制账号权限并记录例外。

## 缺失能力规划

### 第一阶段：安全与可靠性底座

| 缺失能力 | 最小落地点 | 验收标准 |
| ---- | ---- | ---- |
| 密钥管理 | 清除仓库凭据、轮换账号、使用私密配置 | 仓库扫描无可重放凭据 |
| 安全传输 | HTTPS 或明确受限的内网例外 | 传输边界与风险有记录 |
| 统一失败语义 | 脚本错误返回非零退出码 | 调度和 CI 不把失败当成功 |
| 最小权限 | 查询与写入账号按用途拆分或收窄权限 | 日常分析账号不能执行高风险操作 |

### 第二阶段：统一验证入口

- Python 保留轻量语法与针对性测试入口。
- Java 默认单元测试与 benchmark 分离。
- C++ 接入 CTest，并确保 Release 模式仍执行真实断言。
- 在项目文档提供一组可复制的最小验证命令；确认 CI 真实需求后再新增工作流。

### 第三阶段：跨方向治理

- 为审查发现建立状态字段或关闭记录，避免报告长期失真。
- 明确数据知识文档、算法设计文档和线上参照副本的负责人及更新条件。
- 对智能体执行保留最小审计信息：任务、工具、输入范围、版本、结果与失败原因。
- 只有重复出现跨方向编排需求时，才考虑统一 agent runtime；当前两个方向共享规范即可。

## 为什么不创建基础设施 Skill

安全限制、测试门禁和退出码属于必须由代码、配置或 CI 强制执行的确定性规则。把它们做成 skill 只能提醒模型，无法形成可靠控制。

`AGENTS.md` 继续保存跨方向协作规则；`SQL_STYLE.md`、Markdown 规范和算法文档保存领域规则；实际拦截由脚本与测试负责。若未来出现重复的发布、审计或故障处理流程，再为那个具体流程创建窄职责 skill，而不是建立笼统的 `project-foundation` skill。
