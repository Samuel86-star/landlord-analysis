## 拆牌正确性

### AC-SPLIT-01 三带把主牌自己当成对子翼

**严重度**：P0
**证据状态**：`SOURCE_PROVEN`
**范围**：Java 与 C++ 同构，须一起改。

`extractTriples` 在扣掉三张之前调用 `collectPairs`。`count[r] >= 3` 时该点数一定出现在「可用对子」里。对子按基础分升序，**自己是剩余最低对时就会被选成翼**，生成非法 `tripleWithPair(R, R)`，再执行 `count[R] -= 3; count[R] -= 2`，计数变负。

孤立三条（手中没有更低对）几乎必中。`333`、`555+KK`、`KKK+AA` 都会自吃；只有「另有更低对」时才碰巧正确（如 `AAA+33`）。三带一 / 裸三张分支在自吃路径上接近死代码。

```229:251:algorithm/src/main/java/com/mamba/landlord/algorithm/splitter/AbstractHandSplitter.java
    protected void extractTriples(int[] count, List<Combo> combos) {
        for (Rank r : ALL_RANKS) {
            int idx = r.ordinal();
            if (count[idx] < 3) continue;
            List<Rank> pairs = collectPairs(count);
            // ...
            if (pairs.size() >= 1) {
                Rank p = pairs.get(0);
                combos.add(Combo.tripleWithPair(r, p));
                count[idx] -= 3;
                count[p.ordinal()] -= 2;
```

`collectPairs` 不过滤主牌：`AbstractHandSplitter.java:311-319`。C++ 同构：`algorithm/native/include/landlord.h:743-766,810-818`。指标期最优拆牌器已正确排除主牌：`algorithm/native/extracted/optimal_split.h:170-171`。`Combo.tripleWithPair` 不做同点校验。无测试覆盖真实 `extractTriples`。

**影响**：

- `V_combo` 走三带二（offset=10）而不是三条（offset=5）；孤立高三条（如 AAA）会虚高约 12 分。
- 手数 `N` 与剩余牌错误；双路径比分可能选中非法拆法。
- 生产过滤、采样阈值、API `handStrength` 全部吃这套分。

**建议**：先 `count[r] -= 3` 再选翼，或 `collectPairs` / `collectSingles` 排除当前主牌。补回归：`333`、`555+KK`、`AAA+33`、`KKK+AA`。Java/C++ 同步改。改完必须重跑 `DealDistributionSampler`，旧 P5/P95 不能复用。

### AC-SPLIT-02 顺子路径会拆散炸弹；高置信短路使双路径无法纠错

**严重度**：待整手回归后再定（初稿误标 P0）
**证据状态**：现象 `SOURCE_PROVEN`；对 `V_total` 的量化影响 `PENDING_TEST`

这里是两件相关、但不应绑成一个 P0 的事。

**现象一（顺序）**：`StraightPrioritizedSplitter` 在裸三、对子、单牌之后才 `extractAllBombs`。四张同点在炸弹分支执行前通常已经不够 4 张。初稿写成「拆成两对或四张单」不精确：当前顺序是先 `extractAllBareTriples`，完整四张会变成**三条 + 单张**。若顺子先吃掉其中 1 张，则只剩一条裸三。炸弹价值丢失的结论仍成立，残牌形态应以可执行测试锁定。

```17:26:algorithm/src/main/java/com/mamba/landlord/algorithm/splitter/impl/StraightPrioritizedSplitter.java
        tryExtractRocket(count, combos);
        while (extractStraights(count, combos)) {}
        while (extractConsecutivePairs(count, combos)) {}
        extractAllBareTriples(count, combos);
        extractAllPairs(count, combos);
        extractAllSingles(count, combos);
        extractAllBombs(count, combos);
```

**现象二（短路）**：注入 scorer 时，命中高置信规则会直接返回单路径，根本不比较两个拆法（`DefaultComboExtractor.java:42-44`）。这破坏类注释写的「双路径取优」契约。`numBombs` 只扫 3–A，四张 2 不计入决策特征（`DefaultSplitterFactory.java:165-172`）。

候选反例（须先写成测试，再谈严重度）：`3–9` 各 1 张 + 四张 8，规则 1 会走高置信顺子；顺子吃 1 张 8 后剩裸三。飞机/炸弹路径会先提炸弹。四张 2 在顺子路径里会变成三条 2 + 单 2。分数差未实测，初稿「大约高 20+ 分」降为待测。

**不建议**让顺子路径也先提取全部炸弹。那样两条路径会趋同。更小的修复是：先修 AC-SPLIT-01；删除高置信单路径返回；永远跑两条路径，按修复后的 `V_total` 取优。只有性能测试证明双路径过贵，才重新设计短路。当前没有证据表明这里值得优化。

## P1 发牌公平性与接线

### AC-CONC-01 静态拆牌器共享可变 `segmentResult`

**严重度**：P1
**证据状态**：`SOURCE_PROVEN`

`DefaultComboExtractor` / `DefaultSplitterFactory` 持有静态 splitter。`findLongestConsecutiveSegment` 把结果写进实例字段再返回引用（`AbstractHandSplitter.java:25,80-99`）。Spring 单例 + `GET /api/shuffle` 并发时，线程 A 写入、线程 B 覆盖，A 再用脏的 `startIdx/maxLen` 扣牌。可错拆，也可 `IndexOutOfBoundsException`。C++ 用栈上 `Segment`，无此问题。

**建议**：返回局部 `int[2]`；静态 splitter 改为无状态，或每请求新实例。加并发拆牌压测。

### AC-API-01 `/api/shuffle` 只回点数、丢掉花色

**严重度**：取决于接口定位；源码只能证明「响应不可还原花色」
**证据状态**：行为 `SOURCE_PROVEN`；是否构成缺陷 `DOC_INFERRED`

内部 `Card.equals` 用 rank+suit，响应只序列化 `rank().name()`（`ShuffleAndDealController.java:51-54`）。四张 A 无法区分。若该接口要支撑牌局还原或 54 张审计，这是缺陷；若只是研究/调试看点数分布，则不是。

源码没有 SecurityFilter，也没有注释声明它是对局出口还是研究接口。在定位确认前，不按「正式客户端发牌出口」定罪。

### AC-API-02 响应携带重洗与牌力

**严重度**：同上，取决于接口定位
**证据状态**：行为 `SOURCE_PROVEN`；「泄露」指控 `DOC_INFERRED`

产品 PRD 写过滤不暴露「是否重洗」给前端或玩家（`deal-balancing-product-prd.md:469`）。控制器把 `reshuffled`、`reshuffleCnt`、三家 V_total / EHS 全部放进 HTTP 响应（`ShuffleAndDealController.java:40-62`）。

若 `/api/shuffle` 是研究/调试接口，返回这些字段合理。若直接服务正式客户端，PRD 约束才适用。当前源码不足以证明它属于哪一种。

### AC-DEAL-01 Java 洗牌不可复现

Spec 要求固定输入可复现。Java 使用 `Collections.shuffle(..., RandomGenerator.getDefault())`，无种子（`DefaultShuffleDealStrategy.java:59-64`）。C++ 有 `ShuffleDealStrategy(uint32_t seed)` 且测试覆盖。Java 侧无法复现 bad case，也无法做同种子 A/B。

**建议**：`shuffle(long seed)` + 无参走 `SecureRandom`；实验与采样必记 seed、configVersion、算法版本。

### AC-DEAL-02 达上限 fail-open，且无法观测「被迫接受」

达 `maxReshuffleTimes` 后无条件接受最后一副牌（`DefaultReshuffleDealStrategy.java:94-116`）。这是设计上的 fail-open，但产品要求记录 `accepted` / `triggerRule` / `configVersion` / `dealCostMs` / `roomId`。实现只打 strengths/ehs/reshuffleCnt。`application.properties` 也没有 `landlord.shuffle-strategy.version`。

被迫接受率（产品目标 &lt;1%）算不出来。阈值过严时极端局仍发出去，却看起来像过滤成功。

**建议**：返回/日志增加「最后一副是否仍 extreme」；达上限打 WARN；采样器输出 forced-accept 率与各规则触发占比。

### AC-DEAL-03 生产过滤只控 17 张静态 V_total

代码里有 `calcPotentialLandlordScore`、`calcMaxLandlordAdvantage`，但生产配置把它们和单牌/炸弹结构维全部关掉（`application.properties:51-61`，值为 `Infinity` 或 `0`）。生效的只有 lower/upper/spread，且都作用在**不含底牌的 17 张**上。

地主优势公式还是「20 张地主分 − 两家 17 张农民均值」（`AbstractShuffleDealStrategy.java:216-234`），量纲不一致。这与 `makedeal-delta-power-stage-report.md` 已验证的结论同构：3×17 静态量对底牌补炸、地主胜率方差完全失明。

技术 PRD §六写五维全开，与 properties 不一致。产品若要「对局均衡」而不只是「开局手感」，必须启用 20 张口径并单独标定。

### AC-ONLINE-01 本快照里房间阈值 JSON 与 loader 键对不上

**严重度**：对快照为接线不匹配；对线上未定级
**证据状态**：快照 `SOURCE_PROVEN`；是否生产事故 `NEEDS_ONLINE_CONFIRM`

`makedeal.json` 提供 `HandCardScore.v1` + `HandCardScore.roomids`（`:784-807`）。`InitEvaluateSysForClassic` 读取 `HandCardScore.BaseScore` 和 `HandCardScore.ShuffleStrategy`（`zgdatbl.cpp:11297-11313`）。在**当前快照**里两者对不上，该函数对这份 JSON 恒为 no-op。

`previous/` 是线上参照副本，不是已核验的部署包。不能据此写成「线上 420/742 过滤已失效」。正确动作是向线上负责人核实实际 `makedeal.json`、loader 和发牌入口版本，再判断有没有真正的接线事故。

在确认之前：**不要用本仓 Java 阈值解释线上体验**，也不要把本条当作已发生的生产故障。

## P1 数据分析口径

### AC-ETL-01 `bomb_0_games` 分桶打不中无炸局

**严重度**：P1
**证据状态**：`SOURCE_PROVEN`（脚本公式；未回放数仓结果）

编码：`1` = 无炸，否则 `bomb_bet/2` = 打出炸数（`dws_ddz_daily_game.md:80`）。StarRocks 的 `/` 是浮点除，`1/2 = 0.5`，`= 0` 打不中。

```81:84:ops/py/batch_insert_allgame_stat.py
        COUNT(CASE WHEN g.bomb_bet / 2 = 0 THEN 1 END) AS bomb_0_games,
        COUNT(CASE WHEN g.bomb_bet / 2 = 1 THEN 1 END) AS bomb_1_games,
        COUNT(CASE WHEN g.bomb_bet / 2 = 2 THEN 1 END) AS bomb_2_games,
        COUNT(CASE WHEN g.bomb_bet / 2 >= 3 THEN 1 END) AS bomb_3plus_games,
```

无炸会从 `bomb_0/1/2/3+` 里漏掉，下游「首日炸弹档 × 留存」被系统性压低。应写成 `bomb_bet <= 1` 或 `bomb_bet DIV 2`。同系列更糟：`dws_ddz_daily_game.md:401` 用 `bomb_bet > 0` 当「有炸弹」——`1` 也会算进去，几乎全表「有炸」。raw 文档用 `> 1` 才对。

### AC-ETL-02 `play_mode` 硬编码房间清单，`0` 同时表示未识别和 rigged

**严重度**：P1（清单与语义冲突已由源码+知识库证明）
**证据状态**：硬编码 `SOURCE_PROVEN`；改维表前须确认维表唯一性与历史有效期

`batch_insert_ddz_daily_game.py:19-27` 没有 `1124/1125/1126`，它们全部掉进 `ELSE 0`。知识库把 `play_mode=0` 定义成 rigged 判定（`data-gotchas.md:11-14`），表文档写成「0=其他」。新开经典/不洗牌房也会是 `0`，和 rigged 混在一起。`batch_insert_app_silvergame_stat.py` 只收 `play_mode IN (1,2,3)`，1124–1126 的银子金流进不了主表。不洗牌列表含 `22042`，不洗牌设计只认 `421/22039/22040/22041`。

`play_mode` 不能当玩法真值。维表化前先确认 `dq_game_room_config` 对同一 `room_id` 是否唯一、历史分区是否有过改档，避免用当前配置覆盖历史房间属性。这与算法源仓互不阻塞，但不要在未核维表前直接改 ETL。

### AC-DOC-01 倍数分布报告用底分反推房间，且档位错标一档

### AC-PARSE-01 手牌分析管线无法复现 06-26+ 报告

- `ops/py/first-classic-beginner/sql/01_cohort_first3_detail.sql` 仍写「hand_cards 全历史 0 覆盖」，不 SELECT `hand_cards`。
- `run_analysis.py:7-8,27-33` 默认列没有 `hand_cards`，却有已删除的 `bomb_cnt` / `bomb_final`。
- `tokenize_hand_cards`（`run_analysis.py:206-220`）按无逗号、`sj`/`bj` 双字符切牌。现行编码是逗号分隔（`6,q,8,7,...`，`10`/`sj`/`bj`）。现解析器会把逗号当牌、把 `10` 拆成 `1`+`0`。
- 新格式 JSON 已去掉 `bomb_cnt`。模块 E 在 06-26 之后恒为 0。

### AC-CAL-01 留存 D7 文档口径不统一

**严重度**：口径冲突，不是 SQL 技术错误
**证据状态**：规范与模板冲突 `SOURCE_PROVEN`

项目规范采用**含首日**口径：D7 = `+6 DAY`，D30 = `+29 DAY`（`retention-sql-pattern.md:96-104`）。`retention-global.md` 与 `retention-by-mode.md` 的主查询用 `INTERVAL 7 DAY`。财务 / 积分 / deepdive 用 `+6`。

这是口径统一问题。统一时应在规范里写明「含首日、D7=+6」，历史报表保留版本说明，不能静默改完后直接横比。`+7` 在「注册次日起算」口径下可以自洽，只是与本仓库已宣布的口径不一致。

`shuffle_times` 在 DWS 用 `IFNULL(..., 0)`（`batch_insert_ddz_daily_game.py:59`）是另一条 `SOURCE_PROVEN` 缺陷：会把「未开启 = -1」吞成「未重洗 = 0」。与 D7 无关，本仓可单独修。

### 评分口径（不是代码写错，但是错误的产品假设）

1. **单牌恒为 0**。孤张 2 的 `V_combo=0`，控制加成还要求 ≥2 张 2。高单只通过手数惩罚和控制加成体现。「无王仍可能中高分、但胜率低」是公式形状，不是数据错。
2. **炸弹/火箭重复计分（PRD 有意）**：炸弹 `V×2+35` 后再 +5 控制；火箭 60 + 大王 5 + 小王 3 + 王炸 5。一手王炸在 `V_total` 里大约贡献 73，牌力桶会被「有没有王」主导。
3. **EHS 不是 Effective Hand Strength**：`1/(1+exp(-V_total/40))`，不参与过滤，没有对手范围、没有剩余牌。字段名会误导成扑克 EHS。应改名 `scoreNorm`。
4. **`V_total` 是静态拆分和**：`ΣV_combo − (N−1)×8 + Control`。不含牌权、配合、叫地主后底牌增益（底牌分支默认关闭）、房间分层、地主/农民不对称。
5. **最少手数 ≠ 最大牌力**：`penaltyPerCombo=8` 下约 20% 手两者不一致。发牌过滤用的是贪心，不是 `optimal_split.h`。
6. **`calcTotalHandScore` 不校验 combo 是否剖分手牌**。非法/漏牌拆法仍会出分。P0-1 因此能静默得分。
7. **三套「牌力」并存**：① 本仓 PRD `V_total`；② 线上 `CalHandCardValue` / `GroupDataExp`（`previous/`）；③ 数仓 `card_power`（06-15 后可信，07 月 PRD 改版 ETL 未切）。handoff 已写明第二断档未进 ETL。用 `card_power` 对账 harness 会错。

## 三套算法不可混用

| 维度 | Java / C++ 拒绝采样 | 线上 previous 拼牌 | extracted harness |
| ---- | ---- | ---- | ---- |
| 策略本质 | 随机 17+17+17+3，极端则重洗 | 定庄 → 做牌配置 → 交错发牌 | Type0/Type1 模拟，用于指标期 |
| 切牌 | 块切 `[0,17)/[17,34)/[34,51)/[51,54)` | 交错 `cards[i*3+seat]` | 依 harness 参数 |
| RNG | Java 无种子；C++ `mt19937` 可种子 | `srand(GetTickCount()+token*10+socket)`，弱且全局 | `--seed`，与线上不同源 |
| 房间 / 身份 | 无 | `MakeDeal[RoomID]`、庄闲、机器人、新用户；本快照 JSON 键与 loader 不对（线上待确认） | 无 |
| 定庄时机 | 发牌后未知地主 | **先 `CalcBanker` 再发牌** | 可选 `--landlord-bottom` |

| 本快照过滤 | Java 三维生效；C++ 默认不过滤 | JSON 读不到，无 isGoodCards 环 | 不发牌 |

### 产品化评估体系（现在只有碎片）

已有：harness 指标（手数/散牌/Δ）、一次 742/420 crossover、房间费率/兑现、新手前 3 局描述、留存框架。缺的是可重复产品化体系：

- **公平性**：座位、房间、策略、保护类型上的牌力/炸/胜率偏差。
- **极端牌**：无炸/多炸/火箭/纯散/牌力左尾的局占比与去向。
- **叫分/抢地主**：无人抢、流局、抢档，按 `shuffle_type` × AI 分层，禁止和 PvP 混比（1125 已是反例）。
- **破产与兑现**：理论倍 vs `real_magnification`，按发牌策略 × 房间档。`real_magnification` 是截断后实现值，不能当理论倍。

- **策略注册表**：房间 → `makedeal.json` 策略名 → 切换日（742=new、420=new2 现在写在散文里）。

没有这套东西，发牌只能「模拟选配、上线赌一把」。

仿真胜率校准（分桶胜率 / AUC）写在评价标准里，代码没有 `V_total → P(win)`。分析已显示无王高分胜率仍低——公式不是胜率，过滤不该假装它是。

## 建议落地顺序

这是风险清单上的优先序，不是任务拆解或工期承诺。

1. **源仓只修已证主链**：AC-SPLIT-01、去掉错误的高置信短路、修掉共享 `segmentResult`，并增加少量整手回归向量（含「长顺+四张」「四张 2」）。不要先改顺子路径「先提全部炸弹」。
2. **Java/C++ 对拍通过后**，重新跑分布采样；旧阈值全部标记失效。用测试结果再决定 AC-SPLIT-02 的严重度，以及是否需要改短路条件。
3. **本仓立即修、与源仓互不阻塞**：`bomb_bet` 分桶、`shuffle_times` 保留 `-1`、手牌解析器、D7 口径说明（统一含首日 `+6`，历史报表加版本注）。
4. **`play_mode` 维表化前**先确认维表唯一性和历史有效期，避免当前配置覆盖历史房间属性。
5. **向线上负责人核实**实际 `makedeal.json`、loader 和发牌入口版本，再判断 AC-ONLINE-01 是否存在真正的线上接线事故。
6. 确认 `/api/shuffle` 的接口定位后，再决定是否改响应形状或拆研究/对局接口。
7. 评估闭环与 Skill 仍排在牌力真值和采样重标定之后。
